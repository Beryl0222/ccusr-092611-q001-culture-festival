# 华服活动编排台说明

华服活动编排台需要在多方参与、事件顺序不稳定和服务重启的情况下保持记录一致。每条记录有所属方、状态和递增版本，所有状态变化写入事件表；请求键用于抵御重复提交，事务失败时整次写入回滚。

## 核心模型

- **场地（venues）**：容量是硬约束，预计人数超限即视为编排冲突。
- **节目（programs）**：保存当前生效编排（场地、时间、人数、依赖、是否需要设备安全确认）与递增版本号。版本 0 表示草稿；每次变更生效版本 +1。
- **变更请求（changes）**：只保存补丁（patch）。提交时做一次冲突预检并随记录返回；三方会签齐全后以**当时的**当前版本为基准重新合并、重新校验，通过才生效为新版本——审批期间其他先生效的变更不会悄悄被覆盖。任一角色可驳回。
- **安全确认（safety_confirmations）**：按（节目， 版本）记录。新版本产生后旧确认自动失效，必须对当前版本重新确认；未确认的节目在发布环节被拦截（422，列出被阻断节目）。
- **发布单（publications）**：按天记录，状态为 succeeded / superseded / rolled_back。重新发布会把旧发布置为 superseded；撤回（rollback）必须填写原因，当前发布置为 rolled_back 并恢复最近的 superseded 为有效日程。受影响节目的待审变更一并置为 superseded，避免基于已撤回编排继续审批。
- **事件（events）**：所有状态迁移的顺序审计流。
- **幂等（idempotency）**：request_key 全库唯一，首次响应落库，重复提交原样返回。

## 冲突检测

候选编排与全库已生效编排比对，冲突逐项列出受影响项目（affected）：

- `capacity_exceeded`：预计人数超出场地容量；
- `double_booking`：同一场地时间区间重叠（半开区间，首尾相接不算）；
- `dependency_timing`：开始时间早于依赖节目的结束时间（含反向：被依赖节目延后波及依赖方）；
- `dependency_unscheduled`：依赖的节目尚无已生效编排。

检测在三个环节执行：变更提交（预检，随记录返回）、审批齐全生效前（复检，冲突则驳回）、发布前（集合兜底）。发布集合内部另做同样校验，保证已发布日程始终一致。

## 持久化

全部状态存于单个 SQLite 文件（默认 ./culture_festival.db，可用 CULTURE_FESTIVAL_DB 指定）。写操作包在 BEGIN IMMEDIATE 事务中，失败整体回滚；服务重启后审批进度、发布状态与幂等记录继续有效。
